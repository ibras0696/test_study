Docker и синтаксис Dockerfile

Один файл с понятной картиной: что такое образ, контейнер, слой, кэш, Dockerfile, Compose и какие правила делают сборку быстрой, маленькой и безопасной.

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["uvicorn", "main:app", "--host", "0.0.0.0"]

1. Что такое Docker

Docker упаковывает приложение вместе с его окружением: Python/Node/Java, системные пакеты, зависимости, переменные, рабочую директорию и команду запуска. Идея простая: приложение должно запускаться одинаково на твоем ноутбуке, сервере и в CI.

Image

Образ. Это шаблон приложения: файловая система плюс инструкция, как запускаться. Образ неизменяемый.

Container

Контейнер. Это запущенный экземпляр образа. Один образ можно запустить много раз.

Layer

Слой. Каждая важная инструкция Dockerfile добавляет слой. Слои кэшируются и переиспользуются.

Главная мысль: Docker не заменяет приложение. Он фиксирует окружение вокруг приложения, чтобы запуск был воспроизводимым.

2. Модель мышления

Dockerfile читается сверху вниз. Docker выполняет инструкции, получает слои и собирает образ. Потом из образа запускается контейнер.

Dockerfileтекстовый рецепт сборки
docker buildисполняет рецепт по шагам
Imageготовый образ приложения
docker runзапускает образ
Containerживой процесс приложения

Что важно не путать

Понятие Что это Пример
Dockerfile Инструкция сборки образа. FROM python:3.12-slim
image Готовый шаблон с файлами и настройками. my-api:1.0
container Запущенное приложение на основе образа. docker run my-api:1.0
volume Постоянное хранилище данных вне контейнера. данные PostgreSQL
network Сеть, через которую контейнеры общаются. API подключается к DB по имени db

3. Dockerfile: базовый синтаксис

Dockerfile обычно лежит в корне проекта и называется именно Dockerfile. В нем нет расширения. Инструкции пишутся в верхнем регистре по соглашению, хотя Docker понимает и нижний.

# Комментарий
INSTRUCTION arguments

# Пример
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "main.py"]

Exec form

Рекомендуемый формат для CMD и ENTRYPOINT. Команда передается как JSON-массив.

CMD ["uvicorn", "main:app", "--host", "0.0.0.0"]

Shell form

Команда запускается через shell. Иногда удобно, но хуже для сигналов и остановки процесса.

CMD uvicorn main:app --host 0.0.0.0

4. Основные инструкции Dockerfile

Ниже самые важные инструкции. Если их понимать, большая часть Dockerfile становится читаемой.

Инструкция Что делает Пример Практический смысл
FROM Выбирает базовый образ. FROM python:3.12-slim С этого начинается почти каждый Dockerfile.
WORKDIR Задает рабочую директорию внутри контейнера. WORKDIR /app После этого команды выполняются из /app.
COPY Копирует файлы с хоста в образ. COPY . . Добавляет код приложения в образ.
ADD Похожа на COPY, но умеет URL и распаковку архивов. ADD app.tar.gz /app Используй редко. Для обычных файлов лучше COPY.
RUN Выполняет команду во время сборки образа. RUN pip install -r requirements.txt Установка зависимостей, системных пакетов, сборка проекта.
CMD Команда по умолчанию при запуске контейнера. CMD ["python", "main.py"] Можно переопределить через docker run image другой-командой.
ENTRYPOINT Фиксированная команда запуска. ENTRYPOINT ["python"] Часто используют для CLI-образов.
ENV Задает переменную окружения. ENV PYTHONUNBUFFERED=1 Доступна во время сборки и запуска.
ARG Переменная только для сборки. ARG APP_VERSION=dev Передается через --build-arg.
EXPOSE Документирует порт приложения. EXPOSE 8000 Не публикует порт сам. Для публикации нужен -p.
USER Меняет пользователя внутри контейнера. USER app Для продакшена лучше не запускаться от root.
HEALTHCHECK Проверяет, живо ли приложение. HEALTHCHECK CMD curl -f http://localhost:8000/health || exit 1 Оркестратор видит не только процесс, но и здоровье сервиса.

5. Слои и кэш сборки

Docker кэширует каждый шаг. Если инструкция и файлы для нее не изменились, Docker берет старый слой из кэша. Поэтому порядок инструкций сильно влияет на скорость сборки.

FROMБазовая система и runtime.
COPY depsФайлы зависимостей: requirements.txt, package.json.
RUN installУстановка зависимостей. Этот слой дорогой, его важно кэшировать.
COPY srcКод приложения. Меняется чаще всего.
CMDКоманда запуска контейнера.
Правило кэша:

Сначала копируй то, что меняется редко. Потом ставь зависимости. Только после этого копируй весь код.

Плохо 
FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
CMD ["python", "main.py"]

Любое изменение кода ломает кэш перед установкой зависимостей.

Лучше 
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "main.py"]

Зависимости переустанавливаются только если изменился requirements.txt.

6. Готовые примеры Dockerfile

FastAPI-приложение

FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8000

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

Python с non-root пользователем

FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

WORKDIR /app

RUN addgroup --system app && adduser --system --ingroup app app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY --chown=app:app . .

USER app

CMD ["python", "main.py"]

Node.js multi-stage build

FROM node:22-slim AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci

FROM node:22-slim AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build

FROM nginx:1.27-alpine AS runtime
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
Multi-stage нужен, когда сборка и запуск требуют разного окружения. Например, для сборки нужны компиляторы и dev-зависимости, а в финальном образе они не нужны.

7. Docker CLI: команды для backend-разработчика

Dockerfile сам по себе ничего не запускает. Ты сначала собираешь образ командой docker build, потом запускаешь контейнер через docker run, потом смотришь логи, заходишь внутрь контейнера и проверяешь сеть, порты, переменные и файловую систему.

Минимальный цикл

# 1. Собрать образ из Dockerfile в текущей папке
docker build -t my-api:dev .

# 2. Запустить контейнер и пробросить порт
docker run --rm --name my-api -p 8000:8000 my-api:dev

# 3. Проверить приложение с хоста
curl http://localhost:8000/health

# 4. Посмотреть запущенные контейнеры
docker ps

# 5. Посмотреть логи
docker logs -f my-api
Команда Когда нужна Что важно понимать
docker build -t my-api:dev . Собрать образ из текущей директории. . в конце означает build context: какие файлы Docker видит при сборке.
docker build --no-cache -t my-api:dev . Пересобрать без кэша. Полезно, когда подозреваешь, что Docker взял старый слой.
docker run --rm -p 8000:8000 my-api:dev Запустить контейнер. --rm удалит контейнер после остановки. -p host:container публикует порт.
docker run -d --name my-api -p 8000:8000 my-api:dev Запустить в фоне. -d detached mode. После этого смотри логи через docker logs.
docker run --env-file .env my-api:dev Передать переменные окружения. Секреты лучше передавать при запуске, а не вшивать в образ.
docker exec -it my-api sh Зайти внутрь работающего контейнера. В slim/alpine образах часто есть sh, а не bash.
docker inspect my-api Посмотреть низкоуровневые настройки. Сети, IP, mounts, env, healthcheck, команда запуска.
docker stop my-api Остановить контейнер. Если контейнер запущен с --rm, после остановки он исчезнет.
docker rm my-api Удалить остановленный контейнер. Удаляется контейнер, не образ.
docker rmi my-api:dev Удалить образ. Если от него есть контейнеры, сначала удали контейнеры.
docker system df Понять, что занимает место. Показывает размер образов, контейнеров, volume и build cache.
docker system prune Почистить мусор. Удаляет неиспользуемые контейнеры, сети, dangling images и кэш. Смотри, что подтверждаешь.

Диагностика контейнера

Проверить env и файлы

docker exec -it my-api sh
printenv
pwd
ls -la
cat /etc/os-release

Проверить порт и процесс

docker port my-api
docker logs --tail=100 my-api
docker top my-api
docker stats my-api

8. Docker volumes и networks

Контейнеры временные: их можно удалить и создать заново. Поэтому данные базы, загруженные файлы и кеши хранят в volumes. А связь между контейнерами делают через Docker networks, где сервисы находят друг друга по имени.

Volume

Постоянное хранилище, которым управляет Docker. Лучший вариант для PostgreSQL, Redis data, user uploads и всего, что должно пережить пересоздание контейнера.

docker volume create pg_data
docker run -v pg_data:/var/lib/postgresql/data postgres:16

Network

Изолированная сеть для контейнеров. В одной сети контейнеры обращаются друг к другу по имени контейнера или имени сервиса в Compose.

docker network create backend
docker run --network backend --name db postgres:16
docker run --network backend --name api my-api:dev

Bind mount vs named volume

Тип Пример Когда использовать
Bind mount -v "$PWD":/app Разработка: код с хоста сразу виден внутри контейнера.
Named volume -v pg_data:/var/lib/postgresql/data Данные сервисов: база, storage, кеши, uploads.
Anonymous volume -v /data Редко. Docker сам создает volume без удобного имени.

Команды для volumes и networks

Volumes

docker volume ls
docker volume inspect pg_data
docker volume rm pg_data
docker volume prune

Networks

docker network ls
docker network inspect backend
docker network connect backend my-api
docker network disconnect backend my-api

9. Docker Compose: связь нескольких сервисов

Docker Compose нужен, когда приложение состоит из нескольких контейнеров. Для backend это обычно API, база данных, Redis, worker, scheduler и иногда nginx. Compose поднимает их одной командой и создает общую сеть.

clientбраузер или curl
api:8000FastAPI контейнер
db:5432PostgreSQL по имени db
redis:6379кеш или broker
workerфоновые задачи
Ключевая идея:

Внутри Compose контейнеры обращаются друг к другу по имени сервиса. Не localhost, а db, redis, api. localhost внутри контейнера означает сам этот контейнер.

services:
  api:
    build: .
    ports:
      - "8000:8000"
    env_file:
      - .env
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: app
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  postgres_data:
services volumes networks env_file healthcheck depends_on

10. Синтаксис docker-compose.yml

Compose-файл пишется в YAML. Отступы важны: обычно два пробела. Верхний уровень чаще всего содержит services, volumes, networks, иногда configs и secrets.

Ключ Что делает Пример
servicesСписок контейнеров проекта.api, db, redis
imageИспользовать готовый образ.image: postgres:16-alpine
buildСобрать образ из Dockerfile.build: .
container_nameЗадать имя контейнера.container_name: my-api
commandПереопределить CMD из Dockerfile.command: uvicorn main:app --reload
portsПробросить порт наружу на хост."8000:8000"
exposeОткрыть порт только внутри docker-сети.expose: ["8000"]
environmentПеременные окружения прямо в YAML.DATABASE_URL: postgresql://...
env_fileЗагрузить переменные из файла.env_file: [.env]
volumesПодключить bind mount или named volume../app:/app, pg_data:/data
networksПодключить сервис к сети.networks: [backend]
depends_onЗадать порядок старта сервисов.condition: service_healthy
healthcheckПроверять состояние сервиса.pg_isready, curl /health
restartПолитика рестарта.restart: unless-stopped
profilesВключать сервисы только по профилю.profiles: ["dev"]

Полный пример для backend: API + Postgres + Redis + worker

services:
  api:
    build:
      context: .
      dockerfile: Dockerfile
    command: uvicorn main:app --host 0.0.0.0 --port 8000 --reload
    ports:
      - "8000:8000"
    env_file:
      - .env
    volumes:
      - .:/app
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started
    networks:
      - backend

  worker:
    build: .
    command: python -m app.worker
    env_file:
      - .env
    depends_on:
      - redis
      - db
    networks:
      - backend

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: app
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      timeout: 3s
      retries: 10
    networks:
      - backend

  redis:
    image: redis:7-alpine
    networks:
      - backend

volumes:
  postgres_data:

networks:
  backend:
    driver: bridge

DATABASE_URL внутри Compose

Если приложение запускается на хосте, база может быть localhost:5432. Но если приложение внутри Compose, база должна быть по имени сервиса:

DATABASE_URL=postgresql+asyncpg://app:app@db:5432/app
REDIS_URL=redis://redis:6379/0

11. Docker Compose CLI: запуск, проверка, отладка

Команда Что делает
docker compose upПоднять все сервисы в foreground, логи видны сразу.
docker compose up -dПоднять сервисы в фоне.
docker compose up --buildПересобрать образы и поднять сервисы.
docker compose downОстановить и удалить контейнеры и сеть проекта.
docker compose down -vОстановить проект и удалить volumes. Осторожно: данные БД исчезнут.
docker compose psПосмотреть состояние сервисов.
docker compose logs -f apiСмотреть логи конкретного сервиса.
docker compose exec api shЗайти внутрь запущенного сервиса.
docker compose run --rm api python -m pytestЗапустить одноразовую команду в новом контейнере.
docker compose restart apiПерезапустить сервис.
docker compose configПроверить итоговый YAML после env-подстановок.
docker compose pullСкачать свежие версии образов из registry.

Типовой backend workflow

# Первый запуск
docker compose up --build

# Запуск в фоне
docker compose up -d

# Логи API
docker compose logs -f api

# Миграции
docker compose exec api alembic upgrade head

# Тесты
docker compose run --rm api pytest

# Зайти внутрь API
docker compose exec api sh

# Полная остановка без удаления БД
docker compose down

# Полная остановка с удалением БД volume
docker compose down -v

12. Безопасность и production-подход

✓

Не запускайся от root

Создай пользователя и добавь USER app.

✓

Не используй :latest

Фиксируй версию: python:3.12-slim.

✓

Не клади секреты в образ

Не пиши токены в ENV и ARG. Используй env на runtime.

✓

Добавь .dockerignore

Не копируй .git, venv, кеши, локальные БД.

✓

Чисти кеш пакетов

Например, pip install --no-cache-dir.

✓

Делай healthcheck

Контейнер может быть запущен, но приложение внутри уже сломалось.

13. Финальный чеклист Dockerfile

✓

База конкретная

Не latest, а версия.

✓

Кэш работает

Зависимости копируются и ставятся до копирования всего кода.

✓

Образ не раздут

Нет venv, локальных файлов, кешей, лишних build tools.

✓

Есть .dockerignore

Контекст сборки маленький и чистый.

✓

Команда запуска понятная

CMD или ENTRYPOINT записаны в exec form.

✓

Секреты не в образе

Пароли и токены приходят через переменные окружения на запуске.

Короткая формула:

Dockerfile должен отвечать на четыре вопроса: от чего стартуем, куда кладем приложение, как ставим зависимости, какой командой запускаем процесс.
